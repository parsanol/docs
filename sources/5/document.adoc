This document is part of the Parsanol specifications series that defines
the requirements for grammar authoring, artifact interchange, and model
integration across the Parsanol parsing stack.

== Introduction

A grammar is a normative artifact: its acceptance boundary and the
meaning of its captures deserve the same in-repo treatment as code. PG
therefore carries two authoring facilities in the source file itself:

* *doc comments* — prose attached to a rule, explaining what it parses;
* *test sections* — executable expectations about what the grammar
  accepts, rejects, and captures.

Both compile into the artifact (PN 2), travel under the same checksum,
and are re-runnable by every consumer.

== Doc comments

A comment whose marker is doubled (`##`) is a *doc comment*. Doc
comment lines immediately preceding a rule attach to that rule. Plain
`#` comments remain ordinary comments.

```
## The publisher is the leading organization token. Copublishers
## follow after a slash, each captured as :copublisher.
publisher = ("ISO" / "IEC") as publisher
```

The compiled envelope carries the rule documentation in its `docs`
section; `Artifact#rule_docs` exposes it. Grammar documentation thus
lives where the rule lives and cannot drift into a separate file.

== Test sections

A `test` section declares executable expectations. Multiple sections
are allowed; each may name an entry, and with a single entry the name
is optional.

```
test {
  accept "ISO 8601-1:2019"
  reject "nonsense"
  example "ISO/IEC WD TS 25025" { publisher: "ISO" }
}
```

* `accept <string>` — the input MUST parse.
* `reject <string>` — the input MUST fail to parse.
* `example <string> { key: value ... }` — the input MUST parse, and the
  bound result MUST contain each named pair (a subset match; values are
  strings, integers, or booleans).

Tests run *at compile time*: the build fails on the first failing
expectation, exactly like the lint of PN 1. They are embedded in the
artifact's `tests` section and re-runnable from the artifact
(`Artifact#run_tests`), so a consumer's CI verifies the grammar's
declared behaviour without any additional test scaffolding.

== Authoring ergonomics

* `entry`, `bindings`, `preprocess`, and `test` sections may be
  authored inside the `grammar` block, next to the rules they describe.
* `version` is not a reserved word: rules may be named `version`
  (the version header is positional).

== Relationship to other specifications

* Source language: PN 1. Artifact envelope: PN 2. The `tests` and
  `docs` sections extend that envelope under the same checksum.

== External test suites

Inline tests keep expectations next to the rules; larger corpora live in
`*.pgtest` suite files:

```
suite smoke for entry identifier {
  accept "ISO 8601-1:2019"
  reject "ISO/"
  example "ISO/IEC WD TS 25025" { publisher: "ISO" }
}
```

Suites run against the grammar or artifact with
`parsanol pg test <file> --suite <dir>` and drive the iterative
development loop: change the grammar, run the suite, repeat.

== The development flow

The workflow has three stages with a deterministic contract in the
middle:

. *Binding requirements.* Tests (inline and in suites) state, for
concrete inputs, which captures with which types the grammar MUST
produce. They are deterministic by construction.

. *Grammar iteration.* The grammar author works red-green against those
requirements with the tooling:
`parsanol pg test grammar.pg --suite suites/`,
`parsanol pg parse grammar.pg "input"`,
`parsanol pg repl grammar.pg` — no language binding required.

. *Language-specific data models.* A second programmer implements
classes against the binding-requirements schema
(`parsanol pg schema grammar.pg` — fields, types, cardinalities,
preprocessing, and observed example captures). Conformance is: the
model materializes the schema, the grammar fills it, the tests prove
both.

Non-deterministic special-casing — rules that are not simple data
transformations — is deliberately NOT expressible in PG or its
bindings: such logic belongs at the language-specific data-model
ingestion end, operating on typed fields, never on raw identifier text.

== Tooling

`exe/parsanol pg` (parsanol-ruby) provides:

[cols="1,2"]
|===
| Command | Purpose

| `compile <file.pg> [-o out.json]`
| compile to an artifact envelope

| `test <file> [--suite dir]`
| run inline tests and external suites

| `schema <file>`
| print the binding-requirements schema

| `parse <file> [--entry E] INPUT`
| parse one input; tree + bound captures

| `repl <file> [--entry E]`
| interactive parse loop

| `doc <file> [rule]`
| print rule documentation
|===
